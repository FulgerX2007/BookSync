# BookSync protocol, v1

This is the normative reference for BookSync clients: the cryptography, the vault
format, the server API, the sync algorithm and how browser bookmarks map onto the
vault. Any client (for example a future Go CLI or Safari extension) that follows it
can share an account with the WebExtension.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. The reference
implementation is `extension/src/` (client) and `internal/` (server). Where this
document and the code disagree, that is a bug in one of them.

## 1. Cryptography

All primitives are available in WebCrypto: PBKDF2-HMAC-SHA256, HKDF-SHA256,
AES-256-GCM and SHA-256.

### 1.1 Inputs

| Name | Definition |
|---|---|
| `u` | the normalized username: `trim(username)` lowercased. It MUST match `^[a-z0-9._-]{3,64}$`. |
| `password` | Unicode string, normalized to NFC before encoding as UTF-8. |
| `sid` | the SyncID: 16 random bytes generated by the client at registration. It MUST NOT be sent to the server. |
| `iterations` | the PBKDF2 iteration count stored for the user (at least 600 000). |

### 1.2 Key derivation

```
salt      = SHA-256(utf8("booksync/v1|" + u))
stretched = PBKDF2-HMAC-SHA256(utf8(NFC(password)), salt, iterations, 32 bytes)
authKey   = HKDF-SHA256(ikm = stretched, salt = sid, info = utf8("booksync/v1/auth"), 32 bytes)
kek       = HKDF-SHA256(ikm = stretched, salt = sid, info = utf8("booksync/v1/kek"),  32 bytes)
```

- `authKey` is the only derived value sent to the server. It proves knowledge of
  the password **and** the SyncID.
- `kek` (key-encryption key) is an AES-256-GCM key. It MUST NOT leave the client.
- **Downgrade protection.** A client MUST refuse KDF parameters from the server
  (prelogin and login responses) unless `kdf == "pbkdf2-sha256"` and
  `600000 ≤ iterations ≤ 10000000`. A malicious server can then not weaken the derivation.

**Test vector.** This vector was computed independently with Python's
`hashlib.pbkdf2_hmac` and RFC 5869 HKDF. The 1 000 iterations are below the
production minimum; the vector exists for testing only.

```
u          = "alice"
password   = "correct horse battery staple"
sid        = 000102030405060708090a0b0c0d0e0f
iterations = 1000
authKey    = bb4e76c9004b496b6e50c1845c3a1a3ee6d695c95f1dbef3a76cd6b1213dd01d
kek        = bf7ae07aff0552d9d1f011eae6d27296ea6897b14c47fd28b5cb767a6192829b
```

### 1.3 Vault key

The vault key is 32 random bytes, generated once at registration (and again on key
rotation). It encrypts the vault and is stored on the server only in wrapped form:

```
wrapped = iv(12) ‖ AES-256-GCM(key = kek, iv, aad = utf8("booksync/v1/wrap|" + u), plaintext = vaultKey)
```

- Every encryption MUST use a fresh random 96-bit IV.
- Clients SHOULD hold the vault key as a non-extractable key handle and clear raw
  key bytes as soon as they are wrapped or imported.
- **Password change** re-wraps the same vault key under the new `kek`. The vault is
  not re-encrypted.

### 1.4 Vault envelope

```
envelope = "BSV1" ‖ iv(12) ‖ AES-256-GCM(key = vaultKey, iv, aad = utf8("booksync/v1/vault|" + u), plaintext = gzip(utf8(JSON(VaultDoc))))
```

- The 4-byte ASCII magic `BSV1` identifies the envelope version. The server checks
  only the magic and a minimum length of 32 bytes (magic, IV and GCM tag).
- The AAD binds each ciphertext to its purpose (`wrap` or `vault`) and to its user.
  A server can therefore not swap blobs between users, or pass a wrapped key off as
  a vault.
- A decryption failure MUST be treated as an error, never as an empty vault.

### 1.5 SyncID display format

The SyncID is shown to people, and typed by them, in this form:

```
BS1-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX
```

- The 28 characters after `BS1` are Crockford base32 (`0123456789ABCDEFGHJKMNPQRSTVWXYZ`):
  - 26 data characters: the 16 bytes as one big-endian 128-bit integer `v`, most
    significant digit first;
  - 2 check characters: `v mod 1021`, as a 2-digit base32 number.
- The characters are grouped in fours, joined with `-` after the `BS1` prefix.
- Parsers MUST:
  - ignore case, spaces and dashes;
  - read `I` and `L` as `1`, and `O` as `0`;
  - accept the input with or without the `BS1` prefix;
  - reject a value whose data does not fit in 128 bits, or whose check does not match.
- 1021 is prime. Any single substituted character, or any swap of two adjacent
  characters, therefore changes `v mod 1021`, so the typo is caught before a login
  round-trip.

### 1.6 Server-side storage of `authKey`

The server stores `prefix ‖ Argon2id(authKey, salt = 16 random bytes)`, where `prefix`
is a one-byte parameter-set id. Parameter set 1 is `m = 19 MiB, t = 2, p = 1`, with a
32-byte output. Comparison is constant-time.

- A login for an unknown username still runs a dummy Argon2id, so response timing
  does not reveal whether the account exists.
- The parameter-set id lets the server change Argon2 parameters without invalidating
  stored hashes.

## 2. Vault document

The plaintext inside the envelope is a UTF-8 JSON object:

```ts
type Guid = string;          // 12-char base64url (72 random bits); roots use the fixed GUIDs below
interface VNode {
  guid: Guid;                // MUST equal its key in `nodes`
  kind: 'folder' | 'bookmark';
  title: string;
  url?: string;              // bookmarks only (required for them)
  children?: Guid[];         // folders only (required for them), in display order
}
interface VaultDoc {
  format: 1;
  seq: number;               // +1 per upload; rollback detection (§4.3)
  writtenBy: string;         // deviceId of the uploader
  writtenAt: number;         // ms since the Unix epoch
  nodes: Record<Guid, VNode>;// every node, including the four roots
}
```

**Roots.** The four roots always exist, are folders and have no parent. They use
Firefox's fixed GUIDs:

| GUID | Canonical title |
|---|---|
| `toolbar_____` | Bookmarks Toolbar |
| `menu________` | Bookmarks Menu |
| `unfiled_____` | Other Bookmarks |
| `mobile______` | Mobile Bookmarks |

**Validity.** After decryption, a client MUST validate the document and refuse an
invalid one. A valid tree:

- has all four roots;
- has a matching `guid` on every node;
- has a `url` and no `children` on every bookmark, and `children` and no `url` on
  every folder;
- has no dangling child references;
- gives every non-root node exactly one parent, and gives roots none;
- has no cycles, and every node is reachable from a root.

**Format.** A `format` higher than the client supports MUST produce an "update the
client" error. The client MUST NOT overwrite such a vault.

**Encoding.** Writers MUST emit `url` on every bookmark (possibly `""`) and never on a
folder, and `children` on every folder (`[]` when empty, never `null`) and never on a
bookmark. Readers follow the reference parser:

- unknown header and node fields are ignored;
- a bookmark's `children` and a folder's `url` are dropped;
- `url: null`, `children: null`, a missing `title` or an unknown `kind` make the vault
  invalid;
- `seq` must be a safe integer (|seq| ≤ 2⁵³ − 1);
- `writtenAt` may be any JSON number.

**Not in v1:** separators, tags, keywords, favicons and `dateAdded` (browsers do not
let extensions set it).

## 3. Server API

### 3.1 Conventions

- **Transport.** HTTPS. Clients MUST refuse plain `http:` except for `localhost`,
  `127.0.0.1` and `[::1]`. The server URL may include a path prefix, and the API
  paths below are relative to it.
- **Binary fields** in JSON (`authKey`, `wrappedVaultKey`, `vault`, …) are base64url
  without padding.
- **Errors** look like `{"error":{"code":"…","message":"…"}}`. Clients branch on
  `code`; `message` is for humans. `GET /` is the one non-JSON success response (an
  HTML page for people); its `404` and `405` errors stay JSON like every other route.
- **Unknown fields.** Clients MUST ignore response fields they don't know.
- **Device authentication:** `Authorization: Bearer bst_<base64url of 32 random bytes>`.
  - The server stores only SHA-256 of the token.
  - Tokens expire after `BOOKSYNC_TOKEN_TTL` without use (90 days by default). The
    expiry slides forward, refreshed at most hourly.
- **Body limits.** JSON bodies are capped at 64 KiB. Unknown fields and trailing data
  get `400`; an oversized body gets `413 request_too_large`. A password change that
  carries a rotation may be up to `64 KiB + ⌈limit × 4/3⌉`, where `limit` is the
  account's vault limit (§3.3).
- **Timestamps** in responses are RFC 3339.

### 3.2 Endpoints

| Method and path | Auth | Request | Responses |
|---|---|---|---|
| `GET /` | – | – | 200 HTML: a service-info page for people (status, version, how to connect, this table). Informational only; clients MUST NOT parse it. |
| `GET /healthz` | – | – | 200 · 503 `unavailable` |
| `GET /v1/info` | – | – | 200 `{service: "booksync", protocol: 1, version, status: "ok" \| "unavailable", registrationOpen, maxVaultBytes}`, also when storage is down. `maxVaultBytes` is the server default; an account may have its own limit (`GET /v1/account/usage`). `protocol` is this document's major version. Servers older than this endpoint answer `404`; clients then fall back to `/healthz`. |
| `GET /v1/auth/prelogin?username=` | – | – | 200 `{kdf, iterations}`. An unknown username gets the defaults (`pbkdf2-sha256`, 600000), so prelogin does not reveal which accounts exist. |
| `POST /v1/auth/register` | – | `{username, authKey, kdf, iterations, wrappedVaultKey, deviceName}` | 201 `{userId, deviceId, deviceToken}` · 400 `invalid_request` · 403 `registration_closed` · 409 `username_taken` |
| `POST /v1/auth/login` | – | `{username, authKey, deviceName}` | 200 `{userId, deviceId, deviceToken, wrappedVaultKey, kdf, iterations}` · 401 `invalid_credentials` |
| `POST /v1/auth/logout` | device | – | 204. Revokes only the calling device. |
| `GET /v1/devices` | device | – | 200 `[{id, name, createdAt, lastSeenAt, current}]` |
| `DELETE /v1/devices/{id}` | device | – | 204 · 404 `not_found` (also for another user's device) |
| `POST /v1/account/password` | device | `{currentAuthKey, newAuthKey, kdf, iterations, newWrappedVaultKey, rotation?: {expectedVersion, vault}}` | 204, or 200 `{version}` + `ETag` with `rotation` · 400 · 401 `invalid_credentials` · 412 `version_conflict` · 413 `vault_too_large` |
| `POST /v1/account/delete` | device | `{authKey}` | 204 · 401 `invalid_credentials` |
| `GET /v1/account/usage` | device | – | 200 `{vaultBytes, maxVaultBytes}`: the size of the current vault version (`0` when empty) and this account's limit (§3.3). Servers older than this endpoint answer `404`. |
| `GET /v1/vault` | device | optional `If-None-Match: "<v>"` | 200 octet-stream + `ETag: "<v>"` · 304 · 404 `vault_empty` |
| `PUT /v1/vault` | device | octet-stream envelope; `If-Match: "<v>"` **or** `If-None-Match: *` | 200 `{version}` + `ETag` · 400 `invalid_vault` / `invalid_request` · 412 `version_conflict` · 413 `vault_too_large` · 428 `precondition_required` |
| `GET /v1/vault/versions` | device | – | 200 `[{version, createdAt, deviceName, size}]`, newest first |
| `GET /v1/vault/versions/{version}` | device | – | 200 octet-stream · 404 `not_found` |

**Rules shared by all endpoints:**

- Any endpoint that needs a device returns `401 unauthorized` for a missing, invalid,
  expired or revoked token.
- Unknown routes get a JSON `404 not_found`, and wrong methods a JSON `405 method_not_allowed`.
- **Registration validation:**
  - `authKey` MUST be 32 bytes;
  - `kdf` and `iterations` are validated as in §1.2;
  - `wrappedVaultKey` MUST be 1–256 bytes;
  - `deviceName` MUST be 1–64 characters without control characters.
- **Login failures** are indistinguishable: a wrong username, password or SyncID all
  yield the same `401 invalid_credentials`.
- **Rate limits.** `/v1/auth/*` is limited to 10 requests/min per client IP, and login
  additionally to 5/min per (IP, username). IPv6 clients are grouped by /64.
  - A limited request gets `429 rate_limited` with `Retry-After` in seconds.
  - Behind a proxy (`BOOKSYNC_TRUST_PROXY_HEADERS=true`), the client IP is the
    **rightmost** `X-Forwarded-For` entry.
  - There is deliberately no per-username lockout, which would let anyone lock a user
    out of signing in on new devices.

### 3.3 Vault versions and optimistic concurrency

- Versions are positive integers per user, starting at 1. The current vault is the
  highest version. ETags are strong: `"<version>"`.
- **Writing.** `PUT /v1/vault` with `If-Match: "<v>"` succeeds only if `v` is the
  current version. `If-None-Match: *` succeeds only if the user has no vault yet.
  - Sending both headers is a `400`; sending neither is a `428`.
  - On a mismatch the server answers `412` with `{"error":{"code":"version_conflict","currentVersion":N,…}}`
    and, when a vault exists, `ETag: "N"`.
- **Atomicity.** The compare, the insert of `v+1` and retention run in one immediate
  SQLite transaction, so concurrent writers serialize.
- **Size limit.** Each account has a vault limit: its own, set by the operator with
  `booksync-server quota`, or else the server default `BOOKSYNC_MAX_VAULT_BYTES`.
  - An upload, or a rotation's vault, larger than the limit gets `413 vault_too_large`.
  - Lowering a limit below the current vault keeps the stored versions; only the next
    larger upload is refused.
  - Clients show the use reported by `GET /v1/account/usage` and warn from 80 % of
    the limit, since a refused upload stops syncing until bookmarks are removed or
    the limit is raised.
- **Retention.** After each write the server keeps the newest `BOOKSYNC_VAULT_KEEP_RECENT`
  versions (default 1: the current one), plus the newest version of each UTC day within
  the last `BOOKSYNC_VAULT_KEEP_DAYS` days (default 30). It deletes the rest. With the
  defaults, history is one version per day: every sync from every browser writes a
  version, so keeping the newest few would hold only the last minutes.

### 3.4 Password change and key rotation

`POST /v1/account/password` re-authenticates with `currentAuthKey` and replaces
`authKey`, the KDF parameters and the wrapped vault key. It signs out every other
device.

- **Without `rotation`** (an ordinary password change):
  - the client derives the new keys with the **same** SyncID;
  - it re-wraps the existing vault key (§1.3);
  - the server answers 204.
- **With `rotation`** ("a device was lost"): the client generates a new SyncID and a
  new vault key, and re-encrypts the current tree with that key. It sends:
  - `newAuthKey`, derived with the new SyncID;
  - `newWrappedVaultKey`, the new vault key wrapped under the new `kek`;
  - `rotation.vault`, the re-encrypted envelope;
  - `rotation.expectedVersion`, the version the client re-encrypted (`0` if no vault
    exists).

  In one transaction the server:

  - checks `expectedVersion` (`412 version_conflict` on mismatch);
  - **replaces the whole history** with the new vault, because old versions are
    unreadable under the new key;
  - answers 200 `{version}`.

  The client then shows a new emergency kit. A stolen SyncID and vault key cannot
  read anything written afterwards.

## 4. Sync algorithm

All merging happens on the client; the server is versioned storage. Each client keeps
this state:

- `base`: the last vault it synced;
- `version`: the server version of `base`;
- `lastSeq`: the highest `seq` seen or written;
- an id map from browser ids to GUIDs;
- `skipped`: GUIDs that this browser cannot show.

### 4.1 One run

0. **Skip.** Skip the run when signed out or paused, or while backing off (unless
   forced). Stop with `roots_changed` if the pinned native roots disappeared, and with
   `native_sync_detected` if the browser's own sync owns them and the user has not
   acknowledged that.
1. **Crash recovery.** If a previous apply was interrupted (`pendingApply` is set),
   rebind each unmapped browser node to the GUID of a `pendingApply` node that matches
   it exactly: same parent, kind, title and URL.
2. **Project.** Read the browser tree into a `VaultDoc` (`local`), see §5.
3. **Fetch.** `GET /v1/vault` with `If-None-Match: "<version>"`.
   - 304: `remote = base`.
   - 404: `remote = null`.
   - 200: decrypt and validate.
4. **Rollback check** (§4.3).
5. **Merge.**
   - With no `base` (a new device or a rejoin): `firstSync(local, remote)` (§4.5).
   - Otherwise: `merge3(base, local, remote)` (§4.4).
6. **Guard** (§4.6).
7. **Apply.** Write the difference between `local` and `merged` to the browser (§5.4):
   - if the user edited bookmarks since step 2, restart;
   - persist `pendingApply = merged` first;
   - persist each id-map entry as soon as its browser call returns.
8. **Upload.** If `merged ≠ remote` (or there is no remote):
   - set `seq = max(remote.seq, lastSeq) + 1`, `writtenBy` and `writtenAt`;
   - encrypt and `PUT` with `If-Match` (or `If-None-Match: *`);
   - on 412, restart. The browser already holds `merged`, so the next attempt merges
     it with the newer vault.
9. **Commit.** Persist `base = merged`, `version` and `lastSeq`, clear
   `pendingApply`, and set status `ok`.

A run restarts at most 3 times. After that it reports `conflict_exhausted`, and the
scheduler backs off exponentially with jitter (30 s up to 15 min, honoring
`Retry-After`). Once converged, a run makes no browser writes and uploads nothing.

### 4.2 When runs happen

- Bookmark changes trigger a run after a 3 s debounce.
- A 1-minute alarm polls. A poll is cheap: a 304 and no upload.
- Runs are single-flight. Events during a run cause exactly one follow-up run.
- Bookmark imports are bracketed where the browser reports them: one run after the
  import ends.

### 4.3 Rollback detection

`seq` lives inside the ciphertext, so the server cannot forge it. A run reports
`rollback_detected` if:

- `remote.seq < lastSeq`, or
- `remote` is `null` while `base` exists (the vault was emptied).

The usual cause is an operator restoring a server backup. The user picks one of two
recovery actions:

- **Use this browser's bookmarks** (`use_local`): upload `local` as the new vault with
  `seq = max(remote.seq, lastSeq) + 1`. Use it on the most up-to-date device. Other
  devices then accept the result with a normal merge.
- **Accept the server's version** (`accept_remote`): set `lastSeq = remote.seq` and
  merge normally. The guard stays active, and whatever the backup lacks is dropped.

### 4.4 Three-way merge (`merge3`)

The merge works per GUID and is deterministic, so every device computes the same
result.

**Definitions:**

- An **edit** is a change to `title`, `url` or parent. A change in child order alone
  is not an edit.
- A folder is **reordered** if its children present in both versions appear in a
  different order than in `base`.

| Situation | Result |
|---|---|
| unchanged on both sides | keep |
| changed on one side only | take that side |
| identical change on both sides | take it |
| `title`/`url` changed differently on both sides | remote wins (first-committed wins) |
| parent changed differently on both sides | remote wins |
| added on one side | add |
| deleted on one side; unchanged or only reordered on the other | delete |
| deleted on one side; edited on the other | keep the edited node (edit beats delete) |
| folder deleted on one side; descendants added or edited on the other | the folder stays deleted. Surviving descendants move to the nearest surviving ancestor (Firefox's Dogear rule), falling back to `unfiled_____`. |
| deleted on both sides | delete |
| child order: only one side reordered | that side's order; the other side's new children go after their predecessor |
| child order: both sides reordered | remote order; local-only new children go after their local predecessor, otherwise at the end |
| children not placed by the rules above | appended in GUID order |
| the merge creates a cycle | use the remote parent for nodes in the cycle; if still cyclic, move them to `unfiled_____` |
| roots | never added, deleted, moved or renamed (titles are localized per browser) |

### 4.5 First sync (`firstSync`)

Used by a device without `base`: a new device, or a rejoin after `roots_changed`.

- **Matching.** Local nodes are matched to remote nodes by GUID first; nodes still in
  the id map from an earlier membership keep their GUID. The rest are matched by
  content, top-down:
  - folders by title within their matched parent;
  - bookmarks by URL match key, with the title as tie-breaker;
  - each remote node is matched at most once.
- **URL match key.** The WHATWG-serialized URL without an empty trailing `#`
  (`new URL(u).href`, which lowercases scheme and host, uses punycode and drops default
  ports). It is used only for matching, never to rewrite a stored URL.
- **Result.** The remote tree plus the unmatched local nodes. Nothing on the remote side
  is deleted or renamed. A local GUID that exists remotely as the other kind gets a
  fresh GUID.
- **Re-login.** Signing in again as the **same** user after a revoked token keeps
  `base` and the id map, so it uses `merge3`, not `firstSync`. Deletions made elsewhere
  are therefore not undone.

### 4.6 Mass-deletion guard

- **Trigger.** A merge triggers the guard when the deletions it implies toward either
  side exceed 25 % of that side's nodes and number at least 20. Deletions toward local
  compare `local` with `merged`; deletions toward the server compare `remote` with `merged`.
- **Pausing.** The client stores `{remoteVersion, deletionsToLocal, deletionsToRemote}`,
  reports `needs_confirmation`, and applies nothing.
- **Confirmation.** A confirmation lets a later run through only if that run merges
  against the same `remoteVersion` and deletes no more in either direction. Otherwise
  the user is asked again.

## 5. Browser mapping

### 5.1 Roots

| Vault root | Firefox | Chromium family |
|---|---|---|
| `toolbar_____` | Bookmarks Toolbar | `folderType: "bookmarks-bar"` (legacy id `1`) |
| `unfiled_____` | Other Bookmarks | `folderType: "other"` (legacy id `2`) |
| `mobile______` | Mobile Bookmarks | `folderType: "mobile"` (legacy id `3`), optional |
| `menu________` | Bookmarks Menu | a folder titled "Bookmarks Menu" directly under Other bookmarks |

**Pinning.** The native root ids chosen on first sync are pinned. If a required pinned
root disappears, sync stops with `roots_changed`. "Re-pin and rejoin" resolves the
roots again and runs `firstSync`, which never deletes.

**Chromium specifics:**

- **Account folders.** Chromium 134+ can expose a local and a Google-account folder
  for each `folderType`. The client prefers the one with `syncing !== true`.
- **Native sync.** If a pinned root is synced by the browser's own account sync, the
  client pauses with `native_sync_detected` until the user acknowledges it. Two
  BookSync browsers on one Google account would otherwise duplicate bookmarks forever:
  native sync copies a node, the other BookSync gives it a new GUID, and the cycle
  repeats.
- **Menu folder.** The client reuses an existing "Bookmarks Menu" folder under Other
  bookmarks before creating one, and pins its id. The folder is hidden from
  `unfiled_____`'s children.
- **Mobile bookmarks.** Desktop Chromium hides this folder while it is empty, and the
  API can then neither read nor write it. It is synced only while visible.

**Firefox specifics.** A root that Firefox lacks is left unpinned.

**Unavailable roots.** A root a browser cannot show is carried over from `base` during
projection, so it never reads as a deletion. This covers the menu folder after the
user deleted it, a hidden Mobile folder, and a root Firefox lacks.

### 5.2 What is synced

Synced: folders and bookmarks under the four roots.

Not synced:

- Firefox separators;
- Chromium managed (policy) bookmarks (`folderType: "managed"`);
- nodes marked `unmodifiable`.

These native-only nodes stay in place and are ignored when computing positions.

### 5.3 Projection (browser → `VaultDoc`)

- **GUIDs.** Each browser node gets its GUID from the id map, or a new random GUID that
  is persisted at once. Bindings whose browser node is gone are pruned.
- **URL canonicalization.** Browsers rewrite URLs on save (trailing slash, punycode,
  percent-encoding, an empty `#`). After every create or update, the client stores the
  URL as read back (`nativeUrl`) in the node's id-map entry. While the browser's URL
  still equals `nativeUrl`, projection emits the vault URL instead. Rewrites therefore
  never look like edits and never ping-pong between browsers.
- **Skipped nodes** are vault nodes this browser cannot hold:
  - a URL the browser refuses (Firefox rejects `javascript:`, `chrome:` and other
    privileged schemes);
  - a node whose folder is in an unavailable root.

  Projection re-inserts them from `base` after their nearest surviving earlier sibling,
  so they never look like deletions. A skipped node whose parent the user deleted is
  dropped.

### 5.4 Applying (`merged` → browser)

- **Order of operations:**
  1. creates and moves, per folder, top-down and in merged order;
  2. title and URL updates;
  3. removals, bottom-up.
- **Minimal moves.** Nodes on the longest increasing subsequence of current positions
  stay put; only the others move.
- **Anchor positioning.** Writes are positioned by anchor ("after sibling P", or
  first). The native index is computed from the folder's current children at write
  time. This absorbs separators, skipped nodes, the menu folder, and the browsers'
  different `move` semantics:
  - Chromium counts the target index before the moved node is removed, so a move
    downward needs `+1`;
  - Firefox treats the index as the final position.
- **Safe removal.** Folders are removed with `bookmarks.remove`, which refuses
  non-empty folders. If it refuses, the user added something meanwhile, and the run
  restarts. A bookmark the user just added is never deleted by mistake.
- **Refused nodes.**
  - A refused create or URL update marks the GUID skipped. For a refused update, the
    stale native copy is removed.
  - A native node that `merged` moves into an unavailable folder is removed from the
    browser and marked skipped.
  - Skipped GUIDs are retried on every apply, so they appear once they become placeable.
    They are forgotten once `merged` no longer contains them.

## 6. Local state

The reference client keeps its state in the IndexedDB database `booksync`:

- **`session`**: serverUrl, username, userId, deviceId, deviceToken, the SyncID, the KDF
  iterations and the wrapped vault key.
- **`vaultKey`**: a non-extractable `CryptoKey`.
- **`sync`**:
  - `base`, `version`, `lastSeq`, `skipped`;
  - `pendingApply`, `pendingConfirmation`;
  - status fields, `paused`, `nextAttemptAt`;
  - the root pins, `nativeSyncAck`.
- **`idmap`**: browser id → `{guid, nativeUrl?}`.

Two events clear different amounts of this state:

- **Signing out** clears everything.
- **A `401`** (revoked or expired token) clears only `deviceToken` and `vaultKey`.
  Signing in again therefore resumes a guarded three-way merge.

Neither touches browser bookmarks.

## 7. Clients without a browser tree

A client that is its own bookmark store (the Android app; mobile browsers don't let
other apps read or write their bookmarks) keeps the vault tree itself as `local`.
§5 does not apply: there is no projection, no id map, no `pendingApply`, and there are
no skipped nodes, because such a client can hold every URL. The sync rules of §4 apply
with these adaptations.

### 7.1 One run

The steps of §4.1 become:

1. Snapshot `local`, its edit revision `localRev`, `base`, `version` and `lastSeq`. A
   client MUST NOT hold its state lock across network calls, and runs are single-flight.
2. Fetch, then run the rollback check (§4.3) unchanged.
3. Merge:
   - **First sync (no `base`):** the client MUST be signed out or freshly signed in, so
     `local` holds only the four empty roots. It adopts the remote (`merged = remote`, or
     the empty tree). If `local` has other nodes, it MUST report an error rather than
     merge (`local_not_empty`).
   - **Otherwise:** `merge3`, as in §4.4.
4. Run the guard (§4.6), then upload (§4.1 step 8).
5. **Commit atomically after the upload.** Write `local = merged`, `base = merged`,
   `version` and `lastSeq` in one durable write, and only if `localRev` is unchanged
   since step 1. If the user edited meanwhile, write nothing and restart: `base` is
   unchanged, so the next attempt runs `merge3(base, editedLocal, uploaded)` and keeps
   the edit.

Crash safety follows:

- A crash after a successful upload but before the commit leaves the old `local`,
  `base` and `lastSeq`. The next run computes `merge3(base, local, uploaded) = uploaded`,
  which equals `remote`, so there is no upload and no ping-pong.
- A failed upload writes nothing.

### 7.2 Accounts and local state

- **Sign-in.** Register and Login need a signed-out device, with one exception:
  re-authenticating the same account after a `401` (same server and username, and the
  same `userId` once the login response arrives). That keeps `base`, `lastSeq` and the
  local edits, as in §6.
- **Signing out** clears the local tree with everything else.
- **Local state at rest.** It SHOULD be sealed. The Android app seals one state file with
  AES-256-GCM under a random data key, and wraps only that data key with a
  non-exportable platform key (Android Keystore). If the platform key is lost, for
  example after a backup is restored to another device, the client starts signed out.
- **NFC.** The password is NFC-normalized before key derivation (§1.1). A client whose
  core cannot normalize (Go's standard library cannot) MUST do it in its platform layer
  before passing the password in.

### 7.3 Conformance

`testdata/conformance/` holds a golden corpus generated by the reference client
(`extension/test/conformance/generate.test.ts`). It covers key derivation and wrapping,
the SyncID, vault parsing and validation, tree equality and `diffStats`, `merge3`
(merged tree and stats) and the guard. The Go client (`internal/client`) replays it,
and CI fails if it is stale.

The opposite direction is covered too: `envelope-go.json` and `wrap-go.json` are
written by the Go client, and the reference client must decrypt and parse them. Any
other client SHOULD replay the corpus.
